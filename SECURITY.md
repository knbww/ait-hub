# Безопасность AIT Hub

Hub хранит данные школьников, поэтому к уязвимостям здесь относятся серьёзно.

## Как сообщить об уязвимости

Не открывайте публичный issue. Напишите приватно через
[GitHub Security Advisories](https://github.com/knbww/ait-hub/security/advisories/new). Опишите, как
воспроизвести проблему и что она позволяет сделать. Ответим в течение трёх дней.

Проверять можно демо-копию (https://demo.ait-hub.pages.dev, данные вымышленные) и свой локальный
стек. На рабочем Hub не трогайте чужие данные и аккаунты, не нагружайте сервис и не подбирайте коды.
Тем, кто действует так, мы не предъявляем претензий и с удовольствием благодарим.

## Как устроена защита

Главная граница — база данных. Браузер ничем не управляет: всё, что он показывает или скрывает,
удобство, а не защита. Любое правило держится на уровне Postgres, даже если обратиться к API напрямую.

| Слой | Что делает |
|---|---|
| Гость | Закрыты все таблицы и все функции, кроме двух: проверка кода вступления и сброс пароля по коду. У обеих есть лимит попыток |
| Анкета набора | Только через функцию `apply`: Turnstile (тот же виджет, что у входа в Hub; функция принимает только токены, решённые на aitclub.org с action `apply`), затем `submit_application` с секретным ключом. База проверяет каждое поле, хранит ответы только выбранного департамента, ограничивает заявки с адреса, с почты и всего, повтор запроса не создаёт вторую заявку. Заявки видят директор, куратор и допущенные директором, всегда с кодом второго фактора |
| Вход | Cloudflare Turnstile на входе и регистрации, проверка на стороне Supabase. Пароль от 10 символов, не из утечек (Have I Been Pwned, без передачи самого пароля), bcrypt cost 10 |
| Вступление | Только по коду с ограниченным сроком, затем подтверждение руководителем. До него аккаунт не видит ничего, кроме своего профиля |
| Второй фактор | Если он включён, сессия без кода не значит ничего: украденного пароля мало. Полномочия директора и куратора и чужие контакты требуют сессии с кодом у всех |
| Роли | Row Level Security на каждой таблице. Функции проверки всегда отвечают да или нет, никогда не `null` |
| Файлы | Закрытые бакеты, короткие подписанные ссылки, только разрешённые типы, лимит на участника и на проект. Фото только с согласия |
| Браузер | CSP без `unsafe-eval` и inline-скриптов, Trusted Types, запрет встраивания, HSTS, изоляция окна |
| Уведомления | Только через службы браузеров. Вызов проверяется, каждое событие объявляется один раз |
| Поставки | `ignore-scripts`, зафиксированный lock-файл, проверка подписей пакетов, неделя выдержки для новых версий, действия CI закреплены на коммитах, секреты только на шаге публикации |
| Наблюдение | Ежедневная проверка живых сайтов снаружи, журнал действий сотрудников, CodeQL, Dependabot, gitleaks, OSV-Scanner |

## Что проверяется автоматически

- `npm run test:db` — все миграции и правила доступа на Postgres в WASM, в том числе общие правила для
  любых объектов базы: у каждой таблицы есть RLS, гость может вызвать ровно две функции, у каждой
  definer-функции зафиксирован `search_path`. Запускается в CI.
- `npm run test:stack` — атаки на настоящий локальный Supabase через публичный API, вместе с Security
  Advisor Supabase и `plpgsql_check`. В CI при изменении базы и раз в неделю (`stack.yml`).
- `security-scan.yml` — gitleaks по всей истории и OSV-Scanner, в базе которого есть и вредоносные пакеты.
- Линтер запрещает `eval`, `dangerouslySetInnerHTML` и `innerHTML` в коде Hub.
- `npm run security:live` — живые сайты снаружи: заголовки, TLS, DNS, открытость API. Каждое утро в
  `security-monitor.yml`; при сбое GitHub пишет владельцу.

## CORS

- **Сайты.** Pages по умолчанию отдаёт `Access-Control-Allow-Origin: *`, в `_headers` это убрано.
- **Функция `push`.** Отвечает только адресу Hub.
- **API Supabase (REST, Auth, Storage).** Настроить нельзя: платформа разрешает любой Origin, а Auth ещё
  и отвечает `Access-Control-Allow-Credentials: true`. Угрозы это не создаёт. CORS защищает то, что браузер
  отправляет сам, то есть cookie, а сессия Hub лежит в `localStorage` и уходит заголовком `Authorization`,
  который чужой сайт прочитать не может. Единственная cookie там служебная (`__cf_bm`). Поэтому чужая
  страница может сделать с API только то, что может гость: вызвать две открытые функции с лимитом попыток.
  **Сессию нельзя переносить в cookie, не закрыв это**: тогда такая настройка CORS станет уязвимостью.

## Что осталось за рамками

- API Supabase работает не в зоне Cloudflare клуба, поэтому правила WAF защищают только статические
  сайты. Прокси на Workers сюда не поставлен намеренно: на бесплатном плане лимит 100 000 запросов в
  день, и его легко исчерпать, положив весь Hub.
- Руководитель видит код сброса, который выдаёт участнику, и теоретически может им воспользоваться.
  Это видно в журнале (`reset_code_issued`, `password_reset_by_code`).
- Почта не подтверждается: в клубе нет отправки писем. Занять чужой адрес при регистрации можно, но
  такой аккаунт ждёт подтверждения руководителя.
